Delivered as five stacked branches

The work is delivered as five branches, each building on the previous one, so every step can be reviewed and measured on its own. They start from the upstream branch Nonlinear_helical_couplings plus one commit that adds wall-clock timers. Unlike the development branches, they keep MPI in the code and the build. For a single node, far3d.x is started directly as one MPI process, without mpirun, and all parallelism comes from OpenMP threads.

Every branch has the CMake option FAR3D_MARCH_NATIVE, which compiles for the build machine's CPU (-march=native, or -xHost with the Intel compiler). It was added to the first branch and merged up through the others. It is off by default, because the executable may not run on older CPUs.

1The problem: a block-tridiagonal solve

FAR3d advances the linearised MHD equations implicitly. Each time step solves a linear system whose matrix couples every radial grid point only to its two neighbours. Grouping all unknowns at one radial point into a block gives a block-tridiagonal matrix: blocks on the diagonal and the two off-diagonals, zero everywhere else. As assembled, the blocks are themselves sparse (4.6–10% nonzero), but the factors that the solver stores are dense, so the solver treats every block as a dense matrix.

The Fourier modes split into three toroidal families that do not couple, so there are three independent systems of this shape.

Toroidal familyBlock order mBlock rows nStorage (A, B, C)
Family 1 (11 equations × 93 modes)10233999.3 GiB
Family 2 (11 × 70)7703995.3 GiB
Family 3 (11 × 32)3523991.1 GiB
Total15.7 GiB

This sets the two costs that matter:

  • The factorisation (decbt) is compute-bound. It runs once per run inside linstart, as dense LU factorisations and matrix products on blocks up to 1023×1023.
  • The solve (solbt) is memory-bandwidth-bound. It runs twice per step (predictor and corrector) and reads all 15.7 GiB of factors each time, about 34 GB per step, with only two flops per number read. Its speed is set by how many bytes per second the cores can stream from memory.

2Why MKL did not scale on 32 cores

On a dual-socket Xeon server, each variant was run with 1 to 32 threads. The built-in solver kept improving with threads, but both MKL variants stopped improving at 2–4 threads:

Variant (50 steps)linstart, 1 thrlinstart, 32 thrStepping, 1 thrStepping, best
Built-in solver, original loop order1365 s188 s444 s122 s (32 thr)
Built-in solver, fixed loop order540 s167 s508 s122 s (16 thr)
MKL, LU (dgetrs every step)92.7 s77.1 s128 s93 s (2 thr)
MKL, explicit inverse144 s92.5 s132 s78 s (16 thr)
 Setup took a constant ~22 s in every run. Threads were not pinned in these runs.

Three causes explain this:

  • At most three threads did solver work. The OpenMP loop ran over the three families, so 29 of 32 threads sat idle in decbt and solbt.
  • MKL went single-threaded inside that loop. MKL runs on one thread whenever it is called from inside an OpenMP parallel region. This holds even for a region switched off with IF(.false.), because the nesting level is still above zero. So the 1023×1023 LU factorisations, which would scale well, ran on one core each.
  • All memory sat on one socket. Linux places a page on the socket of the thread that first writes it. The block arrays were zeroed by one thread, so all 15.7 GiB landed on one socket and the other socket's threads read across the inter-socket link.

Turning the family loop off is not enough

Solving the families one after another, outside any OpenMP region, lets MKL thread its own calls again. That fixes the factorisation, since dgetrf and dgemm on 1023×1023 blocks have plenty of work to share. Time stepping still did not scale well. With explicit inverses each solve step is a single dgemv on one block (at most 8 MB), and MKL has to split that small, memory-bound call afresh for every one of the ~2,400 blocks per sweep: it starts and joins its thread team each time, and the threads that read a block are not the ones whose socket holds it.

Time stepping therefore needs parallelism that the solver controls itself: a fixed split of every block over all threads, the same for every call, with each thread always reading the same part of memory. This is the column-panel scheme of section 3.

3Column panels, tuned for 32 cores

The development branch mt_solbt_panels parallelises inside each block row instead of across families. The changes below are listed with the gain each one brought, measured as it was added. They overlap, so they do not multiply to the total. The delivered branch nag_panelized contains the first five changes, and nag_fully_tuned adds the sixth. The last one is a build option on every nag_* branch.

Drop the parallel family loop

Families now run one after another, so MKL is called outside any OpenMP region and threads each LU factorisation over all 32 cores. Made optional on mt_blas_lapack as FAR3D_OMP_FAMILIES, default off.

Every thread streams its own slice of every block, so all 32 cores read memory at once (see the animation below).

NUMA-aware first touch

bt_zero zeroes each panel from the thread that will later stream it, so the panel lands on that thread's socket. Threads are pinned (OMP_PROC_BIND=close, OMP_PLACES=cores), and numactl --localalloc stops the kernel's automatic NUMA balancing from moving pages.

482 → 352 mssolbt per step

Store Aₖ⁻¹Cₖ instead of Cₖ

decbt premultiplies the sub-diagonal block, so each forward row is a single phase yₖ = Aₖ⁻¹yₖ − (Aₖ⁻¹Cₖ)yₖ₋₁ with one barrier instead of two. All three families share that barrier.

Inverse by dgetrs on the identity

MKL's dgetri scales badly to 32 threads (11 ms vs 3 ms at m = 1023). Solving against the identity with dgetrs gives the same inverse faster.

The panel scheme, animated

The example runs the forward sweep and then the backward sweep over 9 block rows with 64×64 blocks, cut into 8×8 tiles. The forward sweep streams two blocks per row (Aₖ⁻¹Cₖ and Aₖ⁻¹); the backward sweep streams one (Aₖ⁻¹Bₖ). With 8 threads, each thread owns one column panel 8 columns wide. Panels are always whole multiples of 8 rows (one 64-byte cache line). Thread t owns columns i₀:i₁ of both blocks and rows i₀:i₁ of the vectors. The real blocks are up to 1023×1023, split over 32 threads, so each panel is about 32 columns wide.

  • Each thread reads only its own panels, which were first touched by the same thread and so live in its own socket's memory. In the default close placement, even threads sit on socket 0 and odd threads on socket 1.
  • Each thread reads only the vector entries it wrote itself in the previous row. Only the small partial-sum buffers (m numbers per thread) cross between threads.
  • One barrier per block row. The partial buffers are double-buffered, so the next row's products can start writing while slow threads still read the previous sums.

With this scheme solbt reads its 34 GB per step in 262 ms with ifx, about 130 GB/s (292 ms with gfortran). A simple OpenMP read test on this machine reaches about 140 GB/s, so the solve runs at roughly 90% of the memory bandwidth available.

4Result accuracy

The delivered branches change the solver's arithmetic in three ways: LAPACK in place of the built-in LU, explicit inverses in place of triangular solves, and a different summation order in the panel products. None of these is exact, so each branch was compared with the built-in solver, nag_fix_rearrange_loop_order, on the 24 text outputs of the 50-step Example run, about 830,000 numbers in total.

Each output column is a time series or radial profile of one quantity or Fourier mode. Differences are measured relative to the largest value in their column. Columns whose largest value is below 1e-3 of the largest value in the same file are reported separately: they hold modes that stay near zero, down to 1e-14 of the file maximum, where any change of rounding shows up as a large relative difference.

  • The move to LAPACK accounts for the whole difference. Explicit inverses and the panel solve add nothing measurable on top of it: all three MKL branches stay within 1e-8 of the built-in solver in every significant column.
  • All branches are reproducible. Two runs of the same branch with 32 threads gave identical numbers. The panel solve and the new parallel loops use a fixed split of the work over the threads, so their summation order does not change from run to run.
  • Parallelising the serial loops does not change results. nag_fully_tuned keeps the per-element summation order and matches nag_panelized exactly.
  • -march=native changes results only at the same rounding level. For each branch, the native build differs from the generic build by at most 8.3e-9 in significant columns, because AVX-512 code uses fused multiply-adds. The native builds give the same picture as the table: within 1.0e-8 of the built-in solver, nag_fully_tuned identical to nag_panelized, and reproducible from run to run.
  • The Intel compiler gives the same accuracy. Each branch built with ifx agrees with its gfortran build to within 8.7e-9 in significant columns, and the ifx builds are also reproducible from run to run. One difference: with ifx, nag_fully_tuned is no longer bit-identical to nag_panelized, differing by up to 8.7e-9. ifx allows floating-point reassociation by default (-fp-model fast), so it may sum the reordered loops in a different order.
  • The near-zero columns differ by up to 1e-5 relative to their own size. In absolute terms no difference exceeds 1e-11 of the largest value in its file.

5What is left

  • MPI in the delivered branches. They still need an MPI library to build, even for a single-node run. Removing it, as on the development branches, would simplify building on a workstation.
  • solbt is at about 80% of measured read bandwidth. Storing the inverses in single precision would halve the traffic, at about 1e-7 relative error per solve; that needs validation.
  • decbt (8.4 s) is MKL dgetrf/dgetrs at m = 1023, which do not scale well to 32 threads. It runs once per run, so it matters most for short runs.
  • Small entries in the factors. The stored factors are dense, but most entries are tiny: in the largest family only about 18% of the entries of Aₖ⁻¹, Aₖ⁻¹Bₖ and Aₖ⁻¹Cₖ exceed 1e-12 of their block’s largest entry, and about 9% exceed 1e-10. Storing only those in a sparse format could cut solbt’s memory traffic several-fold. The drop tolerance would need careful validation, ideally per row rather than per block. Separately, one of the 11 variables never appears in B or C, so 1/11 of the columns of Aₖ⁻¹Bₖ and Aₖ⁻¹Cₖ are exactly zero; skipping them saves about 6% of the traffic at no accuracy cost.
  • Accuracy on other cases. The explicit inverses were checked on the Example case only (section 4). For a new case with possibly ill-conditioned blocks, compare one run against nag_lapack, which keeps the LU factors.
